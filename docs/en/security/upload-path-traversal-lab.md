# Upload and path traversal lab: file names and types from the client (MP-SEC-8)

> Versão em português: [docs/pt/security/upload-path-traversal-lab.md](../../pt/security/upload-path-traversal-lab.md) · Versión en español: [docs/es/security/upload-path-traversal-lab.md](../../es/security/upload-path-traversal-lab.md)

Mini-project: [`projects/security/upload-path-traversal-lab`](../../../projects/security/upload-path-traversal-lab/README.md). Quiz topics: `ssrf-path-traversal-upload`, `csp-security-headers`.

This is a defensive lab. It runs only in Docker, on an internal network, with fake data, and the only file read "from outside" is a fake secret the lab creates in a temporary folder. The vulnerable code exists only to make the flaws observable.

## The concept

A file upload carries the bytes of the file and three descriptions of it. The descriptions are text written by the client:

| What the client sends | What it really is | Who must decide instead |
| --- | --- | --- |
| The file name | A label, possibly containing `/`, `\` and `..` | The server generates the name on disk |
| `Content-Type` | A claim about the content | The server reads the leading bytes |
| `Content-Length` | A claim about the size | The server counts the bytes as they arrive |

**Path traversal** is what happens when a name from the request becomes part of a path. To the operating system, `..` means "the folder above", so a name can leave the folder the application had in mind. The **canonical path** is the single final form of a path after every `.` and `..` was applied and every symbolic link was followed. Two different texts can name the same file, so a decision about a path is only reliable when it is taken on the canonical form.

## The flaw

```text
disk of the lab                         bob-fake -> vulnerable server
<tmp>/uploads/            upload root   GET /download?file=../private/FAKE-SECRET.txt
<tmp>/private/                            join(uploads, "../private/FAKE-SECRET.txt")
    FAKE-SECRET.txt       outside       = <tmp>/private/FAKE-SECRET.txt -> 200, the secret
```

The vulnerable API does `join(uploadRoot, name)` and uses the result, for reading and for writing:

- **Read outside the folder.** The download returns the fake secret. The percent-encoded form of the same name works too, because the URL is decoded before the handler runs.
- **Write outside the folder.** The upload stores the file wherever the name points.
- **Overwrite.** Names are shared, so a second `report.txt` replaces the first, whoever owns it.
- **Type chosen by the client.** The declared `Content-Type` is stored and served back without `nosniff` and without `Content-Disposition`. An HTML page uploaded as `text/html` is served as a page of the application.
- **No size limit.** The whole body is read into memory before anything is checked.
- **Symbolic links are followed.** A link inside the folder that points outside is read like any file.

## The fix

| Layer | What the fixed API does |
| --- | --- |
| Name on disk | `randomUUID()` generated by the server. Written with the `wx` flag, which never replaces a file |
| Original name | Metadata only: validated with Zod, reduced to its last segment, returned in an encoded `Content-Disposition: attachment` |
| Lookup | Download by id: the id is validated as a UUID with Zod and looked up in an index. Unknown ids and other users' files answer `404` |
| Canonical path | `resolve`, require "root + separator" as prefix, then `realpath` (root and file) and require it again. The path that was checked is the path that is read |
| Type | Allow-list decided by the leading bytes: PNG, PDF, plain UTF-8 text. A declared type outside the list, unknown bytes or a mismatch answer `415` |
| Size | The body is read in chunks and cut off at the first byte over the limit: `413` |
| Response | Detected type, `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment`, `Content-Security-Policy: default-src 'none'; sandbox` |
| Process | Non-root `bun` user, upload folder outside any static folder |

The first two rows remove the problem (the client's name is no longer used), and the others are layers that still hold if one of them fails. The separator in the prefix comparison matters: without it, `/data/uploads-old` would count as inside `/data/uploads`.

Two limits are stated in the code. A magic number says how a file starts and proves nothing about the rest, so the response headers are what keep an accepted file inert. And between `realpath` and the read there is a small window (a race called TOCTOU), which is closed in practice by the fact that only the server writes in the folder, under names it generated.

### What is not a fix

- **Removing `../` once**: one pass over the text can leave behind a sequence that becomes `../` afterwards, so the filter and the file system read different strings.
- **Checking the extension**, **trusting `Content-Type`** or **trusting `Content-Length`**: all three are written by the client.
- **A blocklist of extensions**: it has to remember every dangerous case, while an allow-list refuses whatever it does not know.
- **Checking the path only as text**: a symbolic link has an innocent name.

## What the tests prove

| Item | How it is verified |
| --- | --- |
| MP-SEC-8.1 a test reads a file outside the upload folder inside the container | `tests/traversal.test.ts`, "vulnerable API: the flaw is observable": the download of `../private/FAKE-SECRET.txt` answers `200` with `FAKE-SECRET-not-real`, a file created by the lab in a temporary folder. Also the encoded form, the write outside the folder, the overwrite and the followed symbolic link |
| MP-SEC-8.1 trusted type, no size limit | `tests/upload.test.ts`: HTML bytes accepted as `image/png`, served as `text/html` with no `nosniff`, and 1 MiB + 1 byte accepted |
| MP-SEC-8.2 the same test is blocked | `tests/traversal.test.ts`, "fixed API: the same attempts are blocked": the same scenario functions get `400`, and the secret is not in the answer |
| MP-SEC-8.2 valid uploads still work | `tests/upload.test.ts`, "normal use works", for both versions: a text file, a PNG and a PDF go up and come back byte for byte |
| Write outside the folder blocked | The upload named `../private/...` leaves nothing outside; one file appears in the folder, named by a UUID |
| Overwrite impossible | Two uploads with the same name get different ids and the first owner reads her own content |
| Bytes that do not match the declared type | HTML as `image/png`, PNG as `text/plain` and unknown bytes named `chart.png` answer `415` |
| File over the limit | `413` for 1 MiB + 1 byte, nothing stored; a 64 MiB stream is cancelled after the limit; exactly 1 MiB is accepted |
| Encoded traversal `%2e%2e%2f` | `400` on the download parameter |
| Symbolic link not followed | A link in the upload folder pointing to the secret answers `404`; `tests/paths.test.ts` checks `realPathInsideRoot` alone |
| Headers and Zod | `nosniff`, `attachment`, CSP and the encoded original name on every download; malformed ids, names and `Content-Length` answer `400` |
| Lab isolation | `tests/network.test.ts`: a request to `http://example.com` fails from inside the container, and the process is not root |

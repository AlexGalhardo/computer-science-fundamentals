# Isolation levels in PostgreSQL (MP-TX-1)

> Versão em português: [docs/pt/transactions/isolation-levels.md](../../pt/transactions/isolation-levels.md) · Versión en español: [docs/es/transactions/isolation-levels.md](../../es/transactions/isolation-levels.md)

Mini-project: [`projects/transactions/isolation-levels`](../../../projects/transactions/isolation-levels/README.md). Quiz topics: `isolation-levels-anomalies`, `mvcc`, `locking`, `acid-properties`.

## The question

Isolation is the I of ACID: concurrent transactions should not step on each other. Full isolation is expensive, so databases offer levels, and each level lets some anomalies through. The usual table of level against anomaly is memorised and rarely tested. This mini-project tests it.

## The five anomalies

| Anomaly | What goes wrong |
| --- | --- |
| Dirty read | B reads a value A wrote and has not committed. If A rolls back, B used data that never existed |
| Non-repeatable read | A reads the same row twice and gets two values, because B committed an update in between |
| Phantom | A runs the same search twice and a new row appears, inserted and committed by B |
| Lost update | A and B read the same value, each computes a new one in the application and writes it. The last write erases the other |
| Write skew | A and B check the same rule, then write **different** rows. Each write is fine alone, together they break the rule |

## Standard against PostgreSQL

The SQL standard defines the levels by the three phenomena it forbids:

| Level (SQL standard) | Dirty read | Non-repeatable read | Phantom |
| --- | --- | --- | --- |
| READ UNCOMMITTED | possible | possible | possible |
| READ COMMITTED | not possible | possible | possible |
| REPEATABLE READ | not possible | not possible | possible |
| SERIALIZABLE | not possible | not possible | not possible |

"Possible" is a permission, not an obligation, and PostgreSQL is stricter than the standard:

- `READ UNCOMMITTED` behaves as `READ COMMITTED`. There is no level that shows a dirty read.
- `REPEATABLE READ` is snapshot isolation: the transaction sees the database as it was at its first statement, so phantoms do not appear either.
- `SERIALIZABLE` is serializable snapshot isolation (SSI): the snapshot, plus tracking of read/write dependencies between transactions.

The standard's table says nothing about lost update and write skew. The measured matrix, generated by the tests, is in the [README](../../../projects/transactions/isolation-levels/README.md#result-matrix).

## What the matrix teaches

- **READ COMMITTED** (the PostgreSQL default) takes a new snapshot for every statement. Two statements of the same transaction can see different data: non-repeatable reads, phantoms and lost updates all happen.
- **REPEATABLE READ** keeps one snapshot for the whole transaction. Reads are stable. A write to a row that changed after the snapshot fails with SQLSTATE `40001` ("could not serialize access due to concurrent update"), which is what stops the lost update. Write skew passes, because the two transactions write different rows.
- **SERIALIZABLE** also detects the dangerous pattern "each read what the other wrote" and aborts one of them with `40001`. This is the only level that stops write skew.

Two ways of preventing an anomaly appear in the matrix: silently (the snapshot hides the change) or with an error. An error `40001` is not a bug. It is the contract of these levels: **the application must retry the transaction**.

## How the harness works

A race is normally a matter of timing. The harness removes the timing:

1. Three connections are opened: sessions A and B, and an observer outside both transactions.
2. A scenario is a list of steps. Each step names its session. The harness sends one step and waits for it to finish before sending the next.
3. Some steps cannot finish: an `UPDATE` on a row locked by the other session waits. The harness does not guess with a sleep. The observer reads `pg_stat_activity` until the server reports `wait_event_type = 'Lock'` for that session, records the moment, and moves on to the step that releases the lock.
4. Every step is logged with a wall-clock time and monotonic start, blocked and finish times. The tests check that each step started after the previous one finished or was confirmed as blocked.

The log of the last run is in `results/timeline.md`.

## Acceptance criteria

| Item | How it is verified |
| --- | --- |
| MP-TX-1.1 fixed order, proven by a log of timestamps | `tests/harness.test.ts`, and `results/timeline.md` |
| MP-TX-1.2 each anomaly reproduced at the weakest level that allows it and blocked at the next | `tests/matrix.test.ts`, "each anomaly is reproduced at the strongest level that allows it and blocked at the next" |
| MP-TX-1.3 README matrix generated by the tests | `tests/matrix.test.ts`, "result matrix" |

One part of MP-TX-1.2 cannot be met on PostgreSQL: a dirty read cannot be reproduced at any level. The test proves the opposite instead, that `READ UNCOMMITTED` does not show uncommitted data.

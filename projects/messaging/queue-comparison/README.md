# queue-comparison

> Versão em português: [README.pt-BR.md](README.pt-BR.md)

What changes when the same task runs on four different brokers? One "order placed" message triggers one simulated confirmation e-mail, and the same producer and consumer code runs on **BullMQ (Redis)**, **RabbitMQ**, **Kafka** and **SQS (LocalStack)** through one TypeScript interface. The code is the same; the behaviour is not: ordering, what happens when a consumer dies with a message in its hands, and speed all differ, and the tests and the benchmark show how.

Code: MP-MSG-1. Full explanation: [docs/en/messaging/queue-comparison.md](../../../docs/en/messaging/queue-comparison.md). It rebuilds the legacy project `references/projects/message-queues-pubsub` under the rules of this repository.

```
producer --send(orders)--> [ BullMQ | RabbitMQ | Kafka | SQS ] --handler(order)--> simulated e-mail
             OrderProducer            QueueAdapter                 OrderConsumer
```

## Results

Generated by `docker compose run --rm demo`, committed in [results/results.md](results/results.md).

### Behaviour experiments

Ordering: 200 orders sent in sequence, one consumer handling one message at a time. Kafka uses a topic with 3 partitions and the customer id as key; the other brokers use one queue. Redelivery: a consumer **process** receives the message and is killed with `SIGKILL` before acknowledging; a second consumer waits for the message.

| Broker | Received in the order sent | In order per customer (key) | Redelivered after the crash | Delay until redelivery | Signal from the broker |
| --- | --- | --- | --- | --- | --- |
| BullMQ on Redis | yes | yes | yes | 3.0 s (lock expiry) | `attemptsStarted` above 1 |
| RabbitMQ | yes | yes | yes | 0.0 s (connection closed) | `redelivered` flag |
| Kafka | **no** (148 of 200 out of order) | yes | yes | 6.0 s (session timeout) | none: the offset was simply not committed |
| SQS on LocalStack | yes (best effort, not guaranteed) | yes (not guaranteed) | yes | 5.7 s (visibility timeout) | `ApproximateReceiveCount` above 1 |

The same experiments are integration tests (`ts/tests/integration.test.ts`): each broker's guarantees are written in `ts/src/expected.ts` and asserted, so the table is backed by a test, not by one lucky run. For SQS standard queues the order is only observed, never asserted, because the service does not promise it.

### Throughput

5,000 messages per run, 3 measured runs after one discarded warm-up. Messages per second: mean (lowest run to highest run).

| Broker | Produce, msg/s | Consume, msg/s |
| --- | --- | --- |
| BullMQ on Redis | 14,311 (12,464 to 15,824) | 6,175 (4,170 to 7,551) |
| RabbitMQ | 31,186 (28,138 to 35,463) | 14,516 (11,391 to 17,047) |
| Kafka | 52,408 (45,995 to 56,779) | 157,782 (154,176 to 161,883) |
| SQS on LocalStack | 2,645 (2,435 to 2,890) | 1,920 (1,765 to 2,032) |

Machine: AMD Ryzen 7 5700X3D, 16 logical cores, 15.6 GiB visible to Docker (WSL2), Bun 1.4.2. Images: `redis:8.10.2-alpine`, `rabbitmq:4.3.6-alpine`, `apache/kafka:4.3.1`, `localstack/localstack:4.14.0`. Clients: bullmq 6.3.11, amqplib 2.2.0, kafkajs 2.2.4, @aws-sdk/client-sqs 3.1147.0.

Read the numbers with care:

- They compare **client plus broker on one laptop**, single node, no replication. They are not a ranking of the products.
- The SQS row measures LocalStack, an emulator written in Python, over HTTP with at most 10 messages per call. It says nothing about the speed of the real service.
- Kafka reads fast because a consumer fetches large batches from a sequential log and commits one offset for all of them; the queues acknowledge each message.
- Each adapter uses the batching its API offers (500 jobs per `addBulk`, confirms every 1,000 publishes, 500 records per Kafka request, 10 messages per SQS call), which is how each would be used in practice.

- `messaging` / `queue-pubsub-stream`: queue against log, what a slow consumer costs in each
- `messaging` / `delivery-guarantees`: at-least-once, acknowledging after the work, durability settings
- `messaging` / `ordering-partitioning`: order per partition and per key, best-effort order in SQS
- `messaging` / `ack-retry-dlq`: unacknowledged messages returning after a crash, visibility timeout
- `messaging` / `rabbitmq-exchanges-routing`: default exchange, durable queue, prefetch
- `messaging` / `kafka-topics-partitions-offsets`: partitions, keys, consumer groups, committed offsets

## Run

The only requirement is Docker.

```sh
./setup-unix-queue-comparison.sh        # Linux and macOS
./setup-windows-queue-comparison.ps1    # Windows
```

The script builds the image, runs the type check and the unit tests with no network, then tests the brokers **one at a time** on an internal network (start the broker, run its integration tests, remove it), so Redis, RabbitMQ, Kafka and LocalStack are never up together.

## Tests

```sh
docker compose run --rm ts-test          # type check (the four adapters implement QueueAdapter) and unit tests
docker compose run --rm test-bullmq      # also: test-rabbitmq, test-kafka, test-sqs
docker compose down -v
```

Each integration test service starts only its own broker. Per broker: 1,000 messages sent and 1,000 received, the ordering experiment and the redelivery experiment.

## Demo and benchmark

```sh
docker compose run --rm demo
docker compose down -v
```

Starts the four brokers at once (Kafka runs with a 256 MiB heap), runs the experiments and the benchmark on each, prints the tables and rewrites `results/results.md` and `results/results.json`. `BROKERS=kafka,rabbitmq`, `BENCH_MESSAGES=20000` and `BENCH_RUNS=5` change the run.

## Everything is local

- The docker-compose network is `internal`: no container reaches the internet and no port is published on the host.
- SQS is LocalStack. The credentials are the fake strings `fake-lab-access-key` and `fake-lab-secret-key`, and nothing reaches AWS.
- `ts/src/config.ts` refuses to start when a broker address is not the loopback or a docker-compose service name, so the benchmark cannot be pointed at somebody else's broker.
- LocalStack is pinned to 4.14.0, the last image that starts without an account token. Newer images need a real credential and a licence server on the internet.

## Structure

| Path | What it is |
| --- | --- |
| `ts/src/queue.ts` | The contract: `OrderProducer`, `OrderConsumer`, `QueueAdapter` |
| `ts/src/adapters/` | One adapter per broker, and the registry the compiler checks |
| `ts/src/experiments.ts` | Round trip, ordering, redelivery and throughput, written once for all brokers |
| `ts/src/crash-consumer.ts` | The consumer process that is killed in the redelivery experiment |
| `ts/src/expected.ts` | What each broker guarantees, asserted by the integration tests |
| `ts/src/demo.ts`, `ts/src/report.ts` | The demo and the Markdown report |

# idempotency-dlq

> Versão em português: [README.pt-BR.md](README.pt-BR.md)

How does a consumer survive messages that arrive twice and messages that can never be processed? Brokers deliver **at least once**, so duplicates are normal, and one bad message retried forever can stop a queue. This mini-project shows the damage first (a consumer with no protection credits an account 2.5 times too much), then the two standard defences: an **idempotency key store** written in the same transaction as the effect, and **retry with exponential backoff** ending in a **dead-letter queue**.

Code: MP-MSG-2. Full explanation: [docs/en/messaging/idempotency-dlq.md](../../../docs/en/messaging/idempotency-dlq.md).

```
publisher --> [work] --> consumer --ok--> ack
                ^           |
                |           +--failed, attempts left--> [retry.N]  waits base x 2^(N-1)
                +------ TTL expired, dead-lettered back ----+
                            |
                            +--invalid, or no attempts left--> reject --> [dlq]
```

## Two languages, two halves of the lesson

| Folder | What it shows | Needs |
| --- | --- | --- |
| `ts/` | The durable version: RabbitMQ redelivery, a `processed_messages` table with a primary key inserted in the same PostgreSQL transaction as the credit, waiting queues with a TTL per backoff step, and RabbitMQ's dead-letter exchange | RabbitMQ and PostgreSQL in docker-compose |
| `go/` | The concurrency behind it: two goroutines holding the same message at the same instant, a store that checks and marks in two steps (wrong) against one that does both in one critical section (right), on an in-memory at-least-once broker | Nothing: standard library only, no network |

## Results

TypeScript, generated by `docker compose run --rm demo`, committed in [results/results.md](results/results.md). Every message is published twice and the consumer loses the acknowledgement of 20% of the deliveries after applying the effect. Each message credits 1.00.

| Consumer | Messages | Deliveries | Fewest deliveries of one message | Effects applied | Balance | Expected balance |
| --- | --- | --- | --- | --- | --- | --- |
| `naive` | 1000 | 2521 | 2 | **2521** | **2521.00** | 1000.00 |
| `idempotent` | 1000 | 2521 | 2 | 1000 | 1000.00 | 1000.00 |

A poisoned message (valid shape, unknown account) with 4 attempts and a backoff starting at 200 ms, plus a malformed one, among 20 healthy messages:

| Attempt of the poisoned message | Waited since the previous attempt |
| --- | --- |
| 1 | first delivery |
| 2 | 203 ms |
| 3 | 403 ms |
| 4 | 803 ms |

| Message in the dead-letter queue | Given up on attempt | Reason recorded by RabbitMQ |
| --- | --- | --- |
| `malformed` | 1 | rejected |
| `poison` | 4 | rejected |

The malformed message is a **permanent** failure, so it is dead-lettered on sight without spending attempts. The 20 healthy messages were all applied: the bad ones did not hold the queue.

Go, printed by `docker compose run --rm go-demo`:

```
store          deliveries    effects    balance
none                 2494       2494    2494.00
racy                 2494       1019    1019.00
atomic               2494       1000    1000.00
```

The racy store is right most of the time, which is what makes the bug dangerous: it is wrong only when two workers hold the same id at once, so its number changes from run to run. A test forces that interleaving and gets 2 effects every time.

## Run

The only requirement is Docker.

```sh
./setup-unix-idempotency-dlq.sh        # Linux and macOS
./setup-windows-idempotency-dlq.ps1    # Windows
```

The script builds the images, runs the TypeScript type check and unit tests and the Go checks with no network, then starts RabbitMQ and PostgreSQL on an internal network for the end-to-end tests, and removes everything at the end.

## Tests

```sh
docker compose run --rm ts-test   # type check and unit tests (backoff, schema, report)
docker compose run --rm ts-e2e    # the three acceptance tests, against RabbitMQ and PostgreSQL
docker compose run --rm go-test   # gofmt, go vet, golangci-lint, go test -race
docker compose down -v
```

The acceptance tests (`ts/tests/e2e.test.ts`, mirrored in `go/idempotency_test.go`):

1. Without protection, the side effect is applied more than once (one effect per delivery).
2. With the store, 1,000 messages delivered at least twice produce exactly 1,000 effects.
3. A poisoned message lands in the dead-letter queue after the configured attempts, each retry waiting at least its backoff step.

## Limits worth knowing

- The "crash" between the effect and the ack is simulated with a negative acknowledgement with requeue, which is what the broker does when a consumer dies. A real process kill is shown in [queue-comparison](../queue-comparison/README.md).
- Publishing the retry copy and acknowledging the original are two steps. A crash in between duplicates the message, which is acceptable only because the handler is idempotent.
- `processed_messages` grows forever here. A real system expires old ids, and the window must be longer than the longest possible redelivery delay.
- PostgreSQL runs with `synchronous_commit=off` because the lab database is disposable. Transactions stay atomic; do not copy the setting to data that matters.

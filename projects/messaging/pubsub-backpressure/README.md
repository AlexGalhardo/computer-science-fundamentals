# pubsub-backpressure

> Versão em português: [README.pt-BR.md](README.pt-BR.md)

Two questions every messaging design has to answer. **Who receives a message?** One of several workers (a work queue, competing consumers) or every subscriber (publish/subscribe, fan-out). **What happens when the producer is faster than the consumer?** Either a buffer grows until memory runs out, or the consumer pushes back and the producer slows down: backpressure. This mini-project answers both with experiments on RabbitMQ, with a producer and a consumer inside one process, and with a GenStage pipeline in Elixir.

Code: MP-MSG-3. Full explanation: [docs/en/messaging/pubsub-backpressure.md](../../../docs/en/messaging/pubsub-backpressure.md).

```
work queue:  producer -> [tasks] -> worker A | worker B | worker C      each message once
fan-out:     producer -> (fanout exchange) -> [q.A] -> subscriber A
                                           -> [q.B] -> subscriber B      a copy for each

no backpressure:  producer ==push==> [ buffer grows ... ] --> slow consumer
backpressure:     producer <--demand / full queue--  [ bounded ] --> slow consumer
```

## Two languages

| Folder | What it shows | Needs |
| --- | --- | --- |
| `ts/` | Work queue against fan-out on RabbitMQ; prefetch as backpressure between broker and consumer; a bounded against an unbounded queue in one process, with memory measured | RabbitMQ in docker-compose (the memory experiment needs nothing) |
| `elixir/` | A GenStage pipeline: the consumer asks for events and the producer sends only what was asked, against plain `send/2` to a mailbox | Nothing at run time (GenStage is fetched when the image is built) |

## Results

TypeScript, generated by `docker compose run --rm demo`, committed in [results/results.md](results/results.md).

### Work queue against fan-out

| Topology | Queues | Consumers | Messages published | Received by each consumer | Total deliveries |
| --- | --- | --- | --- | --- | --- |
| Work queue: one queue, competing consumers | 1 | 3 | 300 | 102, 100, 98 | 300 |
| Fan-out: one queue per subscriber | 3 | 3 | 300 | 300, 300, 300 | 900 |
| Fan-out to 2 services, 3 instances each | 2 | 6 | 300 | 97, 99, 104, 102, 102, 96 | 600 |

The number of **queues** decides the number of copies, not the number of consumers. The third row is the usual production shape: broadcast between services, competition inside each service.

### Where the backlog lives: RabbitMQ prefetch

A queue starts with 3,000 messages and one consumer that takes 2 ms per message, observed for 600 ms.

| Prefetch | Most messages held by the consumer at once | Left in the broker | Processed |
| --- | --- | --- | --- |
| no limit | 2908 | 0 | 230 |
| 10 | 10 | 2758 | 232 |

Both consumers processed the same amount. Without a limit the broker pushed the whole backlog into the consumer process: the queue looks empty, the consumer's memory holds everything, and a second consumer would get nothing. With `prefetch(10)` the backlog stays in the broker, which is built to hold it.

### Producer faster than consumer, in one process

The producer tries to send 20 messages of 4 KiB per millisecond; the consumer handles one per millisecond. The only difference between the runs is the capacity of the queue between them.

| Buffer | Produced | Consumed | Peak messages waiting | Growth of process memory (RSS) |
| --- | --- | --- | --- | --- |
| unbounded queue | 25920 | 1297 | 24623 | 103.3 MiB |
| bounded queue, capacity 100 | 1388 | 1288 | 100 | -6.7 MiB |

| Time | unbounded queue | bounded queue, capacity 100 |
| --- | --- | --- |
| 5 ms | 0 (0.0 MiB) | 0 (0.0 MiB) |
| 432 ms | 4882 (19.1 MiB) | 100 (0.4 MiB) |
| 872 ms | 8644 (33.8 MiB) | 100 (0.4 MiB) |
| 1292 ms | 13983 (54.6 MiB) | 100 (0.4 MiB) |
| 1709 ms | 20101 (78.5 MiB) | 100 (0.4 MiB) |

The unbounded buffer grows in a straight line for as long as the run lasts: about 45 MiB per second here, with no ceiling except the memory of the machine. The bounded one sits at its capacity, and the producer, made to wait by `await queue.push()`, produced exactly as fast as the consumer consumed. The run is 2 seconds long: "without bound" is shown as growth that never slows down, not by exhausting the memory of the machine.

### GenStage (Elixir)

Printed by `docker compose run --rm elixir-demo`. The consumer takes 1 ms per event.

```
pipeline                            events   peak buffer
push, no backpressure                 1000           999
push, no backpressure                10000          9997
push, no backpressure               100000         99983
GenStage, max_demand 10               1000            10
GenStage, max_demand 10               3000            10
GenStage, max_demand 100              3000           100
```

With `send/2` the buffer is the consumer's mailbox and follows the number of events. With GenStage it follows the configuration: `max_demand`, whatever the number of events.

## Run

The only requirement is Docker.

```sh
./setup-unix-pubsub-backpressure.sh        # Linux and macOS
./setup-windows-pubsub-backpressure.ps1    # Windows
```

The script builds the images, runs the TypeScript type check and unit tests (which include the memory experiment) and the Elixir tests with no network, then starts RabbitMQ on an internal network for the end-to-end tests, and removes everything at the end.

## Tests

```sh
docker compose run --rm ts-test       # type check, bounded queue, memory with and without backpressure
docker compose run --rm ts-e2e        # work queue, fan-out and prefetch, against RabbitMQ
docker compose run --rm elixir-test   # mix format --check-formatted and the GenStage tests
docker compose down -v
```

What the tests assert:

1. A queue delivers each message once: 300 messages, 300 deliveries, shared among 3 workers. A fan-out delivers it to every subscriber: 300 messages, 300 for each of 3 subscribers.
2. Without backpressure the buffer is larger at the end of every quarter of the run and the resident memory grows by more than 15 MiB; with a capacity of 100 the buffer never passes 100 messages and the resident memory grows by less than 10 MiB.
3. A GenStage consumer with `max_demand: 10` never has more than 10 events in flight while 2,000 events pass; plain `send/2` leaves the whole stream in the mailbox.

## Notes

- RabbitMQ 4.3 refuses transient queues that are not exclusive, so the lab queues are declared durable and auto-delete.
- The Elixir image is `elixir:1.20.4-otp-28-alpine`: the slim Debian variant has no CA certificates and cannot reach Hex during the build.
- `gen_stage` is pinned to 1.3.2 in `mix.exs` and `mix.lock`, and the build uses `mix deps.get --check-locked`.

# bun-vs-node

> Versão em português: [README.pt-BR.md](README.pt-BR.md)

The same HTTP API, written once, served in three ways: by Bun, by a single Node.js process, and by Node.js under PM2 cluster mode with four workers. A local k6 scenario loads a CPU-bound endpoint and an I/O-bound endpoint on each setup, and a report turns the runs into a table of requests per second, p95 latency and memory. The lesson is that throughput depends on two separate things: how fast the runtime executes your code, and how many processes the process model lets you use.

Code: MP-PERF-1. Full explanation: [docs/en/performance/bun-vs-node.md](../../../docs/en/performance/bun-vs-node.md).

> **Local only.** k6 runs on an internal Docker network with no published port, and the load script refuses to run when the target is not `localhost` or one of the three services of this docker-compose file. Never point a load test at a host you do not own.

## Quiz topics it demonstrates

- `performance` / `runtime-performance`: the single-threaded event loop, CPU-bound work blocking every other request, cluster mode and its memory cost
- `performance` / `latency-throughput-percentiles`: requests per second against p95 latency, and why both are reported
- `performance` / `benchmarking-methodology`: same workload and same CPU budget for every setup, warm-up that is not measured, several rounds, range reported
- `performance` / `k6-fundamentals`: scenarios, the closed model of `constant-vus`, checks with a threshold, `handleSummary`
- `performance` / `capacity-planning-queueing`: what adding workers can and cannot buy

## Run

The only requirement is Docker.

```sh
./setup-unix-bun-vs-node.sh        # Linux and macOS
./setup-windows-bun-vs-node.ps1    # Windows
```

The script builds the two images, runs the type check and the unit tests, runs one API test suite against the three servers, checks that k6 refuses a target that is not local, and removes the containers at the end.

## Load test (the benchmark)

```sh
./load-test-unix.sh            # Linux and macOS, optional argument: number of rounds
./load-test-windows.ps1        # Windows, optional: -Rounds 3
```

One command, about four minutes with three rounds. For each setup and each round it starts a fresh server container, runs k6 (warm-up, then 8 s on `/cpu`, then 8 s on `/io`), and stops the server, so the setups never compete with each other. Then the report rewrites `results/` and the table above. Raw k6 summaries go to `k6-results/`, which is git-ignored.

Variables: `CPU_LIMIT` (CPUs per server container, default 4) and `WORKERS` (PM2 instances, default 4).

## Tests

```sh
docker compose run --rm ts-test           # type check and unit tests, no network
docker compose run --rm api-test          # one suite against the three servers
docker compose run --rm k6-refusal-test   # k6 must refuse https://example.com
docker compose down -v
```

| What is proven | Where |
| --- | --- |
| The API answers the same on Bun, Node.js and Node.js under PM2 (same primes, same errors) | `ts/tests/api/api.test.ts` |
| One process answers on `bun` and `node`, several on `node-pm2` | `ts/tests/api/api.test.ts` |
| Fifty I/O-bound requests overlap on one event loop | `ts/tests/api/api.test.ts` |
| CPU-bound work keeps a due timer from firing | `ts/tests/unit/work.test.ts` |
| The local-target rule accepts loopback and the three service names, and refuses lookalikes such as `http://localhost@example.com` | `ts/tests/unit/target.test.ts` |
| k6 exits with an error and sends nothing when `BASE_URL` is not local | `load/refusal-test.sh` |
| The report computes median and range, and fails on a missing setup or failed requests | `ts/tests/unit/report.test.ts` |

## API

| Route | What it does |
| --- | --- |
| `GET /cpu?n=200000` | CPU-bound: counts the primes below `n` by trial division (2 to 2,000,000) |
| `GET /io?ms=20` | I/O-bound: waits `ms` milliseconds on a timer, like a query sent to a database (0 to 1000) |
| `GET /health` | Setup, runtime, runtime version and the id of the process that answered |
| `GET /memory` | Memory of the whole container, from the cgroup files |

## Structure

| Path | What it is |
| --- | --- |
| `ts/src/app.ts` | The API, with Zod validation, independent of the runtime |
| `ts/src/work.ts` | The CPU-bound and the I/O-bound work |
| `ts/src/bun-server.ts` | The API on `Bun.serve` |
| `ts/src/node-server.ts` | The API on `node:http`, used alone and by PM2 |
| `ts/ecosystem.config.cjs` | PM2 cluster mode |
| `ts/src/memory.ts` | Memory of the container from cgroup v2 |
| `ts/src/report.ts` | Aggregates the k6 summaries into the table |
| `load/scenario.js` | The k6 scenario |
| `load/target.js` | The rule that refuses targets that are not local |
| `results/` | The committed results |

`load/target.js` is a copy of the rule used by `projects/concurrency/ten-thousand-connections`, with the service names of this project. A mini-project never imports code from another one.

## Versions

| Component | Version |
| --- | --- |
| Bun | `oven/bun:1.4.2` |
| Node.js | `node:24.21.0-bookworm-slim` (LTS) |
| PM2 | 7.0.4, installed with npm in the Node.js image |
| k6 | `grafana/k6:2.3.0` |
| Zod | 4.6.5 |
| TypeScript | 7.0.2 |

Node.js runs the TypeScript source compiled to one CommonJS file by `bun build` (a build stage of `ts/node.Dockerfile`). PM2 is pinned, but npm resolves its own dependencies at image build time, because a global install has no lockfile.

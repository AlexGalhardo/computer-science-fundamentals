# k6-scenarios

> Versão em português: [README.pt-BR.md](README.pt-BR.md) · Versión en español: [README.es.md](README.es.md)

A local API on PostgreSQL with a deliberate bottleneck (a connection pool of 2), and four k6 scenarios that each look at it from a different angle: **load**, **stress**, **spike** and **soak**. Every scenario has thresholds, fails them with the small pool, and passes with a pool of 20. Nothing else changes between the two runs. The lesson is what each type of load test is for, and how a bottleneck that no CPU graph shows appears as a knee in the latency curve.

Code: MP-PERF-2. Full explanation: [docs/en/performance/k6-scenarios.md](../../../docs/en/performance/k6-scenarios.md).

> **Local only.** k6 runs on an internal Docker network with no published port, and the script refuses to run when the target is not `localhost` or the `api` service of this docker-compose file. Never point a load test at a host you do not own.

A scenario fails when it crosses a threshold: p95 latency of 250 ms or more, overall or in any phase, or 1% or more failed requests. Machine, versions and the list of summaries are in [results/results.md](results/results.md). The latency knee is in [results/stress.md](results/stress.md).

## Quiz topics it demonstrates

- `performance` / `load-test-types`: what load, stress, spike and soak tests each reveal, and the shape of each
- `performance` / `k6-fundamentals`: scenarios, the `ramping-arrival-rate` executor (open model), stages, thresholds and exit code 99, checks, tags, `handleSummary`, the target from `__ENV`
- `performance` / `database-performance`: the connection pool, what happens when every connection is busy
- `performance` / `capacity-planning-queueing`: capacity of a pool as connections divided by holding time, the latency knee at saturation
- `performance` / `latency-throughput-percentiles`: p95 against the median, failed requests, latency by phase

## Run

The only requirement is Docker.

```sh
./setup-unix-k6-scenarios.sh        # Linux and macOS
./setup-windows-k6-scenarios.ps1    # Windows
```

The script builds the image, runs the type check, the unit tests and the tests against a PostgreSQL container on an internal network, checks that k6 refuses a target that is not local in each of the four scenarios, and removes the containers at the end.

## Load test (the demo)

```sh
./load-test-unix.sh            # Linux and macOS, optional arguments: pool before, pool after
./load-test-windows.ps1        # Windows, optional: -PoolBefore 2 -PoolAfter 20
```

One command, about six minutes. It runs the four scenarios with a pool of 2 connections, runs them again with a pool of 20, and then the report writes `results/` and the table above. The report fails unless every scenario crossed a threshold before the fix and none after, and unless the stress test shows a latency knee before the fix and none after. Raw k6 summaries go to `k6-results/`, which is git-ignored.

One scenario by hand:

```sh
docker compose up -d --wait api
docker compose run --rm -e SCENARIO=stress -e VARIANT=before k6    # exit code 99: a threshold was crossed
docker compose down -v
```

## The four scenarios

| Scenario | Shape | The question it answers |
| --- | --- | --- |
| `load` | ramp to 150 req/s, hold, ramp down | Does the system meet its service level at the traffic it was built for? |
| `stress` | steps from 50 to 300 req/s | Where does it stop coping, and how does it behave there? |
| `spike` | 40 req/s, 500 req/s for 6 s, 40 req/s again | Does it survive a burst, and how fast does it recover? |
| `soak` | 130 req/s, constant | What degrades only with time? (one minute here, hours in real life) |

All four use the open model (`ramping-arrival-rate`): k6 starts requests at the given rate whether or not the earlier ones were answered. A closed model would hide the bottleneck, because virtual users that wait for their answers slow the load down by themselves.

## Tests

```sh
docker compose run --rm ts-test           # type check, unit tests, tests against PostgreSQL
docker compose run --rm k6-refusal-test   # k6 must refuse https://example.com
docker compose down -v
```

| What is proven | Where |
| --- | --- |
| Six concurrent requests take about six times longer on a pool of 1 than on a pool of 6 | `ts/tests/integration/pool.test.ts` |
| A request that waits longer than the limit gets `503` (load shedding) | `ts/tests/integration/pool.test.ts` |
| Every scenario asks for more than the pool of 2 can serve and at most 60% of the pool of 20 | `ts/tests/unit/profiles.test.ts` |
| Each profile has the shape of its test type | `ts/tests/unit/profiles.test.ts` |
| The report demands fail-before and pass-after, and finds the knee | `ts/tests/unit/report.test.ts` |
| The local-target rule refuses lookalikes such as `http://api.example.com` | `ts/tests/unit/profiles.test.ts` |
| k6 exits with an error and sends nothing when `BASE_URL` is not local | `k6/refusal-test.sh` |

## API

| Route | What it does |
| --- | --- |
| `GET /products/:id` | Reads one product. Holds one pool connection for about `QUERY_MS` (20 ms). `404` unknown id, `503` no connection became free within `POOL_WAIT_MS` (2 s) |
| `GET /stats` | Pool size, open, idle and waiting connections, requests shed |
| `GET /health` | Liveness |

## Structure

| Path | What it is |
| --- | --- |
| `k6/profiles.js` | The four load profiles, as data shared by k6, the tests and the report |
| `k6/scenario.js` | The k6 script: executor, thresholds, tags by phase, summary |
| `k6/target.js` | The rule that refuses targets that are not local |
| `ts/src/db.ts` | The connection pool, the query, the waiting limit |
| `ts/src/app.ts` | The ElysiaJS routes, with Zod validation |
| `ts/src/report.ts` | Builds the Markdown summaries and checks the acceptance criteria |
| `results/` | The committed Markdown summaries, one per scenario |

`k6/target.js` is a copy of the rule used by the other load tests of the repository, with the service name of this project. A mini-project never imports code from another one.

# isolation-levels

> Versão em português: [README.pt-BR.md](README.pt-BR.md)

Which anomaly does each isolation level allow? This mini-project answers by experiment. A two-session harness drives two transactions against a local PostgreSQL in a fixed, logged order, reproduces five anomalies (dirty read, non-repeatable read, phantom, lost update, write skew) at each of the four isolation levels, and writes the result matrix below.

Code: MP-TX-1. Full explanation: [docs/en/transactions/isolation-levels.md](../../../docs/en/transactions/isolation-levels.md).

## Result matrix

Generated by the tests. Do not edit by hand: `docker compose run --rm ts-test` rewrites everything between the markers.

<!-- matrix:start -->
| Anomaly | READ UNCOMMITTED | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
| --- | --- | --- | --- | --- |
| Dirty read | prevented | prevented | prevented | prevented |
| Non-repeatable read | **occurs** | **occurs** | prevented | prevented |
| Phantom read | **occurs** | **occurs** | prevented | prevented |
| Lost update | **occurs** | **occurs** | prevented (error 40001) | prevented (error 40001) |
| Write skew | **occurs** | **occurs** | **occurs** | prevented (error 40001) |
<!-- matrix:end -->

How to read it:

- **occurs**: the anomaly was observed at that level.
- **prevented**: the transaction kept reading its own snapshot, with no error.
- **prevented (error 40001)**: PostgreSQL aborted one transaction with a serialization failure, and the application must run it again.

This is PostgreSQL, not the SQL standard. The standard allows dirty reads at `READ UNCOMMITTED` and phantoms at `REPEATABLE READ`. PostgreSQL treats `READ UNCOMMITTED` as `READ COMMITTED`, so it has **no level that shows a dirty read**, and its `REPEATABLE READ` is snapshot isolation, which shows no phantoms but still allows write skew.

The timestamp log of every interleaving is in [results/timeline.md](results/timeline.md).

## Run

The only requirement is Docker.

```sh
./setup-unix-isolation-levels.sh        # Linux and macOS
./setup-windows-isolation-levels.ps1    # Windows
```

The script builds the image, runs the tests against a PostgreSQL container on an internal network, and removes the containers at the end.

## Demo

```sh
docker compose run --rm demo
docker compose down -v
```

Prints the matrix and, for each anomaly, the step-by-step log with timestamps at the level where it occurs and at the level where it stops.

## Tests

```sh
docker compose run --rm ts-test
docker compose down -v
```

The container runs the TypeScript type check and then `bun test`. The tests prove that the steps ran in the planned order (from the timestamps), that each anomaly occurs at the strongest level that allows it and is prevented at the next, and they regenerate `results/` and the matrix above.

## Structure

| Path | What it is |
| --- | --- |
| `ts/src/harness.ts` | The two-session harness: fixed order, lock-wait detection, timestamp log |
| `ts/src/anomalies.ts` | The five anomalies as scripts of steps |
| `ts/src/matrix.ts` | Runs anomaly against level, renders the matrix and the timelines |
| `ts/src/demo.ts` | The CLI demo |
| `ts/tests/` | Tests of the harness and of the matrix |
| `results/` | Matrix and timestamp log of the last run |

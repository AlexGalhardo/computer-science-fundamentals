# outbox-saga

> Versão em português: [README.pt-BR.md](README.pt-BR.md)

How do two services stay consistent when each has its own database and no transaction can cover both? This mini-project runs an order service and a payment service, each with its own PostgreSQL, talking through RabbitMQ. It shows the **dual-write bug** (commit to the database, then publish: a crash in between loses the event), fixes it with a **transactional outbox**, makes the consumers **idempotent**, and finishes the business flow as a **saga with compensation**: a failed payment cancels the order.

Code: MP-TX-4. Full explanation: [docs/en/transactions/outbox-saga.md](../../../docs/en/transactions/outbox-saga.md).

```
client -> order-service --(orders-db: orders + outbox)--> relay --> RabbitMQ --> payment-service --(payments-db)
              ^                                                                        |
              +----------- PaymentCompleted / PaymentFailed <--- relay <--- outbox ----+
```

## Results

Generated by `docker compose run --rm demo`, committed in [results/results.md](results/results.md):

| Scenario | Mode | Order | Payment | Event reached the payment service |
| --- | --- | --- | --- | --- |
| happy path | `dual-write` | PAID | COMPLETED | yes |
| happy path | `outbox` | PAID | COMPLETED | yes |
| crash between the write and the publish | `dual-write` | PENDING | none | **no, lost** |
| crash between the write and the publish | `outbox` | PAID | COMPLETED | yes |
| payment fails | `outbox` | CANCELLED | FAILED | yes |

The crash is real: the order service calls `process.exit(1)` right after the commit and Docker restarts it.

## Quiz topics it demonstrates

- `transactions` / `saga-outbox`: dual write, transactional outbox, relay, choreographed saga, compensation
- `transactions` / `idempotency`: at-least-once delivery, the idempotent consumer with `processed_messages`, the `Idempotency-Key` header
- `transactions` / `distributed-transactions-2pc`: the problem two-phase commit solves, approached here without a distributed transaction

## Run

The only requirement is Docker.

```sh
./setup-unix-outbox-saga.sh        # Linux and macOS
./setup-windows-outbox-saga.ps1    # Windows
```

The script builds the image, starts the two databases, the broker and the two services on an internal network, runs the end-to-end tests, and removes everything at the end.

## Demo

```sh
docker compose run --rm demo
docker compose down -v
```

Runs the five scenarios of the table, prints them and rewrites `results/results.md`.

## Tests

```sh
docker compose run --rm ts-test
docker compose down -v
```

The container runs the TypeScript type check and then `bun test`: unit tests, and end-to-end tests that talk to the running services over HTTP and to the broker.

## API of the lab

| Service | Route | What it does |
| --- | --- | --- |
| order-service | `POST /orders` | Body `{ orderId, customerId, amountCents, mode, crashAfterCommit }`. `mode` is `outbox` (default) or `dual-write`. Optional header `Idempotency-Key`. `201` created, `200` replayed |
| order-service | `GET /orders/:id` | The order, with `status` `PENDING`, `PAID` or `CANCELLED` |
| payment-service | `GET /payments/:orderId` | The payment, `COMPLETED` or `FAILED` |
| both | `GET /stats` | Unpublished outbox rows (and duplicates skipped, in the payment service) |

Amounts above 500.00 (`50000` cents) are declined by the fake card rule.

## Structure

| Path | What it is |
| --- | --- |
| `ts/src/orders.ts` | Creating an order (dual write and outbox) and the saga step that reacts to the payment |
| `ts/src/payments.ts` | The idempotent handler of `OrderCreated` |
| `ts/src/shared/outbox.ts` | Outbox insert, relay, and the `processed_messages` check |
| `ts/src/shared/broker.ts` | RabbitMQ: publisher confirms and manual acknowledgements |
| `ts/src/shared/events.ts` | The three events and their schema |
| `ts/src/scenarios.ts`, `ts/src/demo.ts` | The scenarios, used by the tests and the demo |
| `results/` | The committed results |

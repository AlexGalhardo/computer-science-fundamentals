# overselling-checkout

> Versão em português: [README.pt-BR.md](README.pt-BR.md) · Versión en español: [README.es.md](README.es.md)

A product has 10 units and 200 people click "buy" at the same instant. A checkout written as "read the stock, check it, write it" sells far more than 10, even inside a transaction. This mini-project reproduces the bug with a local k6 load test against an ElysiaJS API on PostgreSQL, and then fixes it in three ways: an optimistic version column, `SELECT ... FOR UPDATE`, and `SERIALIZABLE` with retry.

Code: MP-TX-2. Full explanation: [docs/en/transactions/overselling-checkout.md](../../../docs/en/transactions/overselling-checkout.md).

## Quiz topics it demonstrates

- `transactions` / `locking`: optimistic against pessimistic locking, `SELECT ... FOR UPDATE`, what a row lock blocks
- `transactions` / `isolation-levels-anomalies`: the lost update at `READ COMMITTED`, and `SERIALIZABLE` with retry on SQLSTATE `40001`
- `transactions` / `acid-properties`: a transaction gives atomicity, which is not isolation
- `transactions` / `mvcc`: readers are not blocked by writers, which is exactly why the naive read is stale

## Run

The only requirement is Docker.

```sh
./setup-unix-overselling-checkout.sh        # Linux and macOS
./setup-windows-overselling-checkout.ps1    # Windows
```

The script builds the image, runs the tests against a PostgreSQL container on an internal network, and removes the containers at the end.

## Load test (the demo)

```sh
./load-test-unix.sh            # Linux and macOS
./load-test-windows.ps1        # Windows
```

One command: it starts the API, runs k6 three times per strategy (200 virtual users, one purchase each), checks that `naive` oversold and that each fix sold exactly 10, and rewrites `results/` and the table above. It fails when any of these checks fails.

k6 only ever targets the `api` service of this compose file: the network is internal, no port is published, and the script refuses a `BASE_URL` that is not local.

## Tests

```sh
docker compose run --rm ts-test
docker compose down -v
```

The container runs the TypeScript type check and then `bun test`. The tests fire the same 200 concurrent purchases in-process and assert the same outcome as the load test.

## API

| Route | What it does |
| --- | --- |
| `POST /checkout/:strategy` | Buys one unit. `strategy` is `naive`, `optimistic`, `pessimistic` or `serializable`. Body: `{ "buyerId": "..." }`. Answers `201` sold, `409` sold out, `503` gave up after too many conflicts |
| `POST /admin/reset` | Body `{ "stock": 10 }`. Deletes the orders and sets the stock |
| `GET /stats` | `{ "stock": ..., "orders": ... }` |

## Structure

| Path | What it is |

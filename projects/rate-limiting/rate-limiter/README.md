# rate-limiter

> Versão em português: [README.pt-BR.md](README.pt-BR.md)

"At most 10 requests per second" sounds like one rule, but five algorithms enforce it in five different ways, and the difference only shows when the traffic comes in bursts. This mini-project implements fixed window, sliding window (log and counter), token bucket and leaky bucket in memory, feeds all of them the same traffic and draws what each one lets through. Then it moves the limiter to Redis, where two application instances share one counter through an atomic Lua script, and shows the race that appears without it.

Code: MP-RL-1. Full explanation: [docs/en/rate-limiting/rate-limiter.md](../../../docs/en/rate-limiting/rate-limiter.md).

## Results

Same 80 requests, every algorithm configured as 10 requests per second. Generated by the experiment into [results/burst.md](results/burst.md).

| Series | under the limit (0-1 s) | burst across a boundary (1-3 s) | sustained overload (3-6 s) | instant burst after silence (6-8 s) | Total | worst 1 s interval |
| --- | --- | --- | --- | --- | --- | --- |
| Offered traffic | 5 | 20 | 40 | 15 | 80 | 20 |
| Fixed window | 5 | 20 | 20 | 10 | 55 | 20 |
| Sliding window (log) | 5 | 10 | 20 | 10 | 45 | 10 |
| Sliding window (counter) | 5 | 11 | 20 | 10 | 46 | 11 |
| Token bucket | 5 | 11 | 29 | 10 | 55 | 19 |
| Leaky bucket (admitted) | 5 | 11 | 29 | 10 | 55 | 19 |
| Leaky bucket (leaving the queue) | 5 | 11 | 29 | 10 | 55 | 10 |

![Requests admitted over time by each algorithm](results/burst.svg)

"Worst 1 s interval" is the largest number of requests let through in any interval of one second, wherever it starts. It is the honest measure of a limit of "10 per second":

- **Fixed window** lets 20 through in 200 ms: 10 at the end of one window and 10 at the start of the next.
- **Sliding log** never exceeds 10, at the price of one stored timestamp per admitted request.
- **Sliding counter** stores two numbers and is off by one here (11), because it assumes the previous window was evenly spread.
- **Token bucket** allows a burst of its capacity and then the refill rate, so up to capacity + rate × time. That is by design: the capacity is the burst you decided to tolerate.
- **Leaky bucket** admits the same requests as the token bucket, but releases them one every 100 ms. A burst goes in, an even stream comes out.

## Quiz topics it demonstrates

- `rate-limiting` / `fixed-window`: aligned windows, one counter per client, the double burst at the boundary
- `rate-limiting` / `sliding-window`: the sliding log and its memory cost, the sliding counter formula and its approximation
- `rate-limiting` / `token-bucket`: capacity as burst size, refill rate as average rate, lazy refill, the cap
- `rate-limiting` / `leaky-bucket`: the queue reading, constant output, comparison with the token bucket
- `rate-limiting` / `redis-distributed`: shared counter, the check-then-act race, the atomic Lua script, `EVALSHA` and `NOSCRIPT`, the Redis clock
- `rate-limiting` / `http-429-and-backoff`: `429 Too Many Requests` with `Retry-After`

## Run

The only requirement is Docker.

```sh
./setup-unix-rate-limiter.sh        # Linux and macOS
./setup-windows-rate-limiter.ps1    # Windows
```

The script builds the images and runs three test suites: the in-memory algorithms in TypeScript, the same in Go (with the race detector), and two application instances sharing one Redis under 400 concurrent requests. It removes the containers and the network at the end.

## Burst experiment (the demo)

```sh
./experiment-unix.sh            # Linux and macOS
./experiment-windows.ps1        # Windows
```

One command: it runs the experiment and rewrites `results/burst.json`, `results/burst.md`, `results/burst.svg` and `results/burst.pt-BR.svg`. The chart is a plain SVG file with no script and no external reference, so it opens from disk in any browser. The experiment is a simulation with an injected clock: it takes milliseconds, sends nothing anywhere and gives the same numbers on every machine. A test fails when `results/` is out of date.

The Go implementation prints the same table: `docker compose run --rm go-test go run ./cmd/experiment`.

## Tests

```sh
docker compose run --rm ts-test             # type check, table of cases, experiment, HTTP answers
docker compose run --rm go-test             # gofmt, go vet, golangci-lint, go test -race
docker compose run --rm distributed-test    # two instances and Redis
docker compose down -v
```

- **Table of cases.** `cases/cases.json` holds 15 timelines ("a request arrives at this millisecond and must be admitted or rejected"), worked out by hand from the definition of each algorithm. TypeScript and Go read the same file.
- **Deterministic clock.** Every limiter receives the time as an argument (`allow(nowMs)`), so no test sleeps.
- **Two instances.** `limiter-a` and `limiter-b` run the same image against one Redis. With the atomic script they admit exactly 50 of 400 concurrent requests, in five rounds. With the naive `GET` then `INCR`, the same crowd gets more than 50 through: up to 192 in the measured rounds, and exactly 50 in a few of them. A race is a matter of timing, which is why the test repeats the round until one exceeds the limit.

## Rules of the lab

Redis and the two instances talk on an internal docker-compose network: no container reaches the internet and no port is published on the host. The concurrent test reads its targets from `TARGETS`, which defaults to the two compose services, and refuses to start when a host is not local.

| `results/` | Output of the experiment |

## Notes

- One limiter object holds the state of one client. A real service keeps a map from the client key to its limiter.
- The leaky bucket is implemented as a queue: `schedule(nowMs)` returns when an admitted request leaves. The first request into an empty bucket leaves at once. Some texts make it wait one interval; the spacing between departures is the same.
- The Redis client is the one built into Bun (`RedisClient`), so the only dependency is Zod, used to validate the cases file, the environment, the query string and the replies of the scripts.
- No code is imported from another mini-project.
